# KnowGrove · 知识森林

KnowGrove 把散落的资料生长成可引用、可研究、可输出的知识树，让 Obsidian 成为一套本地优先的自生长知识研究工作台。

一个围绕“阅读状态 + 段落评论 + 稳定双向引用 + 属性工作流”设计的 Obsidian 插件。

## 已实现功能

### 工作台

- 左侧 Ribbon 的“工作台”只保留“已符合规范 / 待规范”两个指标；属性检查标题右侧提供快速设置和重新检查入口，点击指标可直接打开对应文档清单。
- 点击“待规范”不再只打开一张静态文章列表，而是进入逐篇处理中心：每篇笔记会列出缺失字段、当前值、原因和建议动作；确定性问题可单篇修复，领域/主题等语义问题可让 AI 先生成建议，确认后再写入。
- 处理中心支持按当前审计结果批量交给 AI：只处理被标记为需要判断的语义字段，先确认范围，再分批并发写入；已有字段会经过值变化校验。
- 新文档进入阅读文件夹后会在后台完成规范处理；工作台不展示重复的过程提示，只通过“已符合规范 / 待规范”指标反映结果，也可以随时手动重新检查。
- 设置页顶部采用“AI 自动搭建分类树”的单一入口：AI 根据现有笔记标题和分类汇总给出完整建议，用户只需选择“直接使用”或“暂不使用”，不再逐字段搭建属性体系。
- 分类策略固定为四层正交结构：`领域树 → 区块维度 → 概念索引 → PDSA 知识循环`。领域最多两级；类型/项目等横向维度保持独立；具体概念留在主题与双链；状态围绕计划、实践、研究和应用推进。
- 当前领域树会直接展示在设置页。用户不满意时只需展开“微调领域树”，按“一级领域/二级领域”修改少量节点；被采用的树会成为后续 AI 自动填写的语义边界。
- 扫描整个 Vault 的现有 frontmatter，检查必备属性、值类型、旧字段和枚举规范；检查本身不会修改笔记。
- 规范检查区分“确定性修复”和“语义判断”：缺失字段、旧属性迁移、单值/多值格式可以预览后自动修复；类型、状态、领域和主题的语义冲突只报告，不按文件夹猜测或覆盖。
- 批量执行前展示文件级差异；执行过程中若失败，会在未发生二次编辑的前提下回滚本次已写入文件。
- 工作台的“成长工作台”采用统一的 `领域 → 主题 → 工作空间` 结构，并分成“研究 / 项目 / 生活”三个入口。研究空间承载课题，项目空间承载推进与交付，生活空间承载生活目标和例行事项；三种场景共享同一套主题树和资料关系。
- 项目空间可创建父项目和子项目，并提供目标、里程碑、关联资料、行动、交付物与复盘区；生活目标和例行事项提供目标/规则、行动、记录与复盘区。空间文件和配套 Base 都保存在 `_KnowGrove/工作空间/`，可以随 Vault 同步。
- 项目按 `领域 → 主题 → 项目` 展示，生活空间按主题展示；标题旁数字是真实关联资料数。资料可以位于 Vault 任意目录，关系依赖 Obsidian Wikilink，而不是依赖文件夹位置。
- 每个工作空间都可以手动搜索并勾选资料，也可以让当前 AI 模型从本地标题、领域和主题中提出相关资料建议。AI 只做预选，用户保存后才建立 `所属项目` 或 `所属空间` 双向关系；取消最后一个关系时不会留下空属性。
- 正式主题按主领域组成知识树，右侧数字分别统计该领域、主题或课题实际关联的资料篇数。现有 `主题` 属性只负责提供“待确认主题”，不会把几百个候选概念直接混入正式知识树。
- 课题不再只是主题文档里的字符串，而是 `_KnowGrove/课题/<主题>/<课题>.md` 下可同步、可重命名的真实 Markdown 节点；它通过 Wikilink 连接上级主题，并拥有独立的核心问题、资料范围和 Base 工作面。
- 1.1.0 的知识树节点支持直接展开/收起。课题会先从全库标题、属性和正文中生成“相关候选”，候选与正式采用资料分开；展开课题即可在左侧浏览候选，点击资料后进入“左侧原文、右侧课题汇总”的双窗格研究模式。
- 1.1.1 将主题与课题树改为单一受控展开状态：展开只负责显示子级，不再触发双窗格或全库重扫；同时修正主题行列数和各层缩进，避免 hover 闪烁、行高跳变和偶发折叠失效。
- 1.2.0 不再把几十或上百篇“候选资料”写入课题属性。候选及排除状态保存在随 Vault 同步的课题 sidecar 中，课题正文末尾提供可交互的“资料筛选”区：点击资料会替换左侧原文，用户可直接标记相关或不相关，也可调用当前配置的 AI 模型批量筛选并在确认后应用。
- 1.2.1 将“资料筛选”中的候选资料图标、标题和路径统一左对齐，短标题与长标题保持相同起点。
- 1.2.2 固定工作台的横向布局，避免反复展开和刷新后树形界面偏移；待确认主题默认完整展开并按领域分组。主题重命名会同步关联笔记的 `主题` 属性，修改所属领域会同步主题、课题和关联资料的 `领域` 属性，同时保留其他主题仍需使用的领域。
- 1.2.3 禁止把插件内部的资料清单写进可见属性：新建主题、课题、项目和生活空间不再生成 `资料范围 / 课题范围 / 子空间`；现有长引用会迁移为反向分类关系或课题 sidecar 后自动清理，正文保持不变。
- 1.2.4 默认开启跨文档块引用拖放：在编辑模式选中文字后拖到另一篇 Markdown，插件会引用选区所在的完整 Markdown 块，自动为源块补稳定块 ID，并在目标位置插入原生 `![[源文档#^块ID]]`；源内容不会被移动或复制，后续修改会同步展示。设置中可随时关闭。
- 1.2.5 为真实鼠标操作增加独立拖动手柄：选中文字后，评论按钮旁会出现“移动”图标，从该图标拖到另一篇文档即可插入块引用，避免 Obsidian 实时预览拦截直接拖动选区。
- 1.2.6 让块引用段落继承当前文档的正文字号、字体和行高；失效引用提示不再以加粗标题干扰正文。拖放会等待源块 ID 进入 Obsidian 元数据缓存后再插入目标，减少短暂的“未找到块”提示。
- 相关资料可以直接拖到右侧插入原生 Wikilink；也可以在左侧原文选中一个区块，通过课题研究台的“引用左侧选区”插入稳定块嵌入。引用内容随原文更新，并纳入课题的正式资料关系。
- 每个课题文档提供“管理相关资料 / 双窗格研究 / 引用左侧选区 / 创作”四个动作。“创作”会进入分步工作室，从本课题的已采用资料和候选资料中批量勾选真正要使用的材料。
- 2.1.0 创作工作室支持微信公众号、小红书、Medium、X / Twitter、Reddit、通用长文、调研报告和内容大纲八种模板。系统会读取全部选中材料并按长度分批提炼证据，不再静默限制为前 12 篇。
- 创作默认采用“选择材料 → 选择方向 → 确认提纲 → 生成初稿”流程；用户可以在生成全文前修改章节、目标和配图提示词。正文是普通 Obsidian Markdown，证据使用原生 Wikilink，配图方案以折叠区块保留。
- 作品的完整材料集、证据摘要、提纲、配图建议和 AI 初稿版本保存在 `_KnowGrove/.data/outputs/` 的同步 sidecar 中，不把长来源列表写进属性，也不会覆盖原始材料或用户后续修改。
- 2.2.0 为生成后的作品增加右侧“创作助手”，统一提供方向、提纲、证据、配图和版本五个工作面。打开 KnowGrove 作品时可以从命令面板唤起；生成首稿和渠道稿后会自动打开。
- 证据审查会逐段检查作品中的事实、数字、因果判断和重要结论，区分“有依据 / 依据不足 / 存在冲突 / 待人工判断”，并可定位回正文原句和打开对应本地证据；审查只报告，不会修改正文。
- 在编辑器选中文字后，可从右键菜单或命令面板调用“AI 编辑选中内容”，完成改写、精简、扩写、改变语气、补充证据和渠道适配。结果先预览，可选择插入到下方或替换；替换 KnowGrove 作品前会自动保存版本。
- 提纲工作面支持按已确认提纲重写单个章节；版本工作面支持手动保存、并排对比和恢复。恢复前会再次保存当前内容，避免覆盖用户后续编辑。
- “生成渠道版本”会把现有作品另存为微信公众号、小红书、Medium、X / Twitter、Reddit、通用长文、调研报告或内容大纲作品包，包含标题候选、摘要、正文、行动引导、配图简报和发布前检查；原稿不会被覆盖。
- 配图默认只保留方案和可复制提示词。用户在“创作与配图”中显式启用并保存图片接口密钥后，可从创作助手生成真实图片，保存到 Vault 附件目录并以 `![[附件路径]]` 插入作品。密钥使用 Obsidian SecretStorage，不写入 `data.json`。
- 每个主题或课题都可以维护 0、1 或多篇资料。用户在设置中确认资料后，插件会只补充对应的主题/课题 Wikilink，不覆盖其他属性；AI 只读取所选资料，结论中的证据使用原生 Wikilink 指回来源。
- 旧版 `研究课题` 字符串会继续作为兼容节点显示，只有用户打开、创建或保存时才转成真实课题文件；升级不会静默批量迁移历史笔记。
- “AI 规划课题与资料”采用两级相关性处理：插件先在本地按标题、领域和主题筛选候选，模型再给出课题和资料建议；建议只在界面中预选，用户确认保存后才会写入主题属性。
- 点击主题会按需创建 `_KnowGrove/主题空间/<主题>.md` 和同名 `.base`：Markdown 负责可同步、可编辑的人类知识结构，Base 展示本次研究资料以及 D/S/A 分组。原始资料保持在原位置。
- 主题空间的 P 研究计划和“已确认知识”完全由用户维护；插件只更新专属 Base 和带明确标记的 AI 建议区块，不覆盖人工内容或用户手工创建的同名文件。
- 主题卡片的 AI 整理入口会读取最多 30 篇相关资料的受限正文片段，生成研究维度、命题候选、证据链接、知识缺口和输出方向；采用前先预览，证据路径必须来自本次输入资料。
- 输入资料、知识笔记、项目、行动和内容输出继续作为内容角色：通常分别支持 D、S 或 A，但不再被错误地当成知识生命周期本身。
- 新建或导入阅读跟踪文件夹的材料，可自动补齐最小输入结构：`文件名 / 类型 / 状态 / 创建时间 / 阅读状态 / 领域 / 主题`。已有值一律保留，创建日期来自文件 ctime，历史笔记不会使用运行日期回填。

### AI 自动属性

- 自动检测桌面端的 Codex CLI、Claude Code CLI、Antigravity CLI（`agy`）、Qoder CLI、Kimi Code CLI、MiniMax CLI（`mmx`）、GLM 的 `zai/glm` 兼容 CLI 与 CodeBuddy CLI；模型会优先以下拉列表展示已检测的默认值和官方预设，只有列表没有目标时才填写自定义 ID。也支持 Anthropic API，以及 Ollama、LM Studio 等 OpenAI 兼容接口。Antigravity 使用 `agy --print --sandbox`，不会为属性处理开放写权限。
- WorkBuddy 会显示本机安装检测，但由于目前没有稳定公开的非交互文本 CLI 协议，插件不会把它用于属性生成，避免误调用。GLM 的直接 CLI 调用属于 `zai/glm` 兼容方式，连接测试通过后才可使用。
- Qoder 的连接诊断会明确区分模型/套餐权限问题；Antigravity 的服务端拒绝会提示检查 CLI 登录、账户权限与服务地区，而不是仅显示笼统的执行终止错误。
- 采用 AI 分类方案后，`类型 / 状态 / 领域 / 主题` 统一由模型在固定契约内判断；文件名、创建时间和阅读状态继续由确定性规则处理。旧用户尚未采用新方案前会保留原有开关。
- AI 生成分类树时只发送相对路径、标题和现有分类汇总，不发送正文；方案只保存到插件设置，采用方案也不会自动批量改写笔记。
- 新文档开启 AI 自动处理后，不会先给语义字段写入空列表；插件等待模型返回非空、通过类型和枚举校验的结果后再写入。
- 模型使用固定 JSON 协议，只能返回配置中允许的属性和值；无效枚举、空字符串、空数组、未知字段和类型不匹配的状态都会被拒绝。
- 自动模式只补缺失值，不覆盖采集器或用户已有属性；命令面板的“AI 刷新当前笔记属性”是显式覆盖入口，工作台的批量处理在执行前会显示文档数量并要求确认。
- 批量补齐采用每批 12 篇、最多 3 批并发；每篇正文只发送截断后的必要片段，批次失败会自动重试。每篇属性成功写入后，默认会同步整理正文的多余空行；关闭“处理时整理多余空行”开关即可跳过。每批完成立即写入，重新执行时会自动跳过已有有效属性，实现断点续跑。
- CLI 通过无 shell、只读沙箱和临时工作目录运行；API Key 使用 Obsidian SecretStorage，不写入插件 `data.json`。长文仅发送配置上限内的开头和结尾，正文不会被修改。

### 阅读列表

- 指定一个文件夹，自动统计未读和已读文档数量；无状态的新文档也会归入未读，不会从列表消失。
- 侧栏只保留一组“未读 / 已读”统计筛选，默认打开未读，并提供标题/路径搜索和紧凑文档列表。
- 文档行使用常规字重；右侧对勾可直接切换“未读 / 已读”，三点菜单可定位原始目录、复制绝对路径或复制仓库相对路径。
- 新建或导入跟踪文件夹的 Markdown 文档，如果还没有状态，会自动写入 `阅读状态: 在看`；启用属性初始化后，也会补齐固定的最小输入结构。普通移动和启动扫描不会批量补核心属性。
- 在实时阅览（Live Preview）或阅读视图主动滚动、点击，并到达文末停留一段时间后，会自动切换为 `阅读状态: 已读完`。
- 可在侧栏、文件右键菜单或命令面板中切换“在看 / 已读完”。
- 已有笔记不会被静默覆盖；可在设置页手动将“未分类”批量补齐为“在看”。
- 空行整理不再提供单独入口：待规范笔记交给 AI 处理并成功写入属性后，会按默认开关同时将文首、段落间和文末空行统一为固定格式；YAML、代码块、数学块、注释及原始 HTML 代码区保持原样。

“读到文末自动完成”默认开启，停留时间默认为 3 秒，可在插件设置中调整为 1–10 秒或完全关闭。实时阅览中发生文字编辑后的 5 秒内不会自动完成；刚打开笔记而没有滚动或点击时也不会自动完成。

### 评论与双向引用

1. 在编辑模式选中一段内容。
2. 选区右上角会显示一个浮动评论图标；点击后直接在右侧打开当前文档的评论栏，不再弹出大窗口。
   - 图标默认完全隐藏，只在当前 Markdown 编辑器存在非空文字选区时出现；它固定跟随选区末端右侧，选区取消、切换页面或滚出编辑区后立即隐藏。
3. 在评论栏顶部输入并保存评论；同一文档的全部评论会集中显示，点击任意评论的原文摘要即可定位到对应文字。上下滚动正文时，评论栏也会跟随突出当前区域的评论。
4. 每条评论底部都有“添加到文档”入口，可搜索目标笔记和选择标题位置；添加后会直接显示目标文档链接。
5. 插件为原文添加稳定的 Obsidian 块 ID，并在编辑与阅读模式为被评论文字加下划线。删除评论时，下划线与目标文档中的受管引用区块会同时移除。
6. 目标笔记插入带唯一 ID 的受管区块，包含：
   - `![[原文#^块ID]]` 原生块嵌入；
   - 评论；
   - 返回原文的块链接。

原文内容修改后，目标笔记中的嵌入会由 Obsidian 自动显示最新内容。通过右侧评论栏修改评论时，插件会同步更新目标笔记中的评论副本。右键菜单和命令面板仍作为备用入口保留。

从 `0.1.4` 开始，创建引用时会先强制保存源区块锚点，再写入目标笔记。插件启动和源文档变化后也会自动检查锚点：若块 ID 被误删，会先按唯一原文定位，原文被改写时再用保存的前后文定位并安全补回。也可执行命令 `KnowGrove: 检查并修复评论引用` 手动审计全部记录；无法唯一定位时只报告问题，不会猜测或误绑。

> [!important]
> 目标笔记中 `knowgrove-ref` 标记之间的内容由插件管理。请通过右侧评论栏编辑评论；手动修改这个区块后，下次同步会以插件中的评论为准。

## 状态数据格式

默认使用中文属性，名称和值都可在设置中修改：

```yaml
---
阅读状态: 在看
---
```

读完后：

```yaml
---
阅读状态: 已读完
---
```

工作台的推荐核心结构为：

```yaml
---
文件名: "当前文件名"
类型: 输入资料
状态: 待整理
创建时间: 2026-07-19
阅读状态: 在看
领域:
  - AI产品
主题:
  - 知识管理
  - 自动分类
---
```

未启用 AI 时可以继续使用空列表作为结构占位；启用后，AI 管理字段会等待模型生成有效值，不再先写空列表。插件不会删除未知属性，也不会在没有预览确认的情况下批量迁移历史文档。采用分类树只是建立规则，真正处理历史笔记仍需从工作台显式发起并确认。

## 安装

### 本地开发安装

```bash
npm install
npm run build
```

将以下三个文件复制到仓库的 `.obsidian/plugins/knowgrove/`：

- `main.js`
- `manifest.json`
- `styles.css`

然后在 Obsidian 的“设置 → 第三方插件”中重新加载并启用 KnowGrove。

### 直接在插件目录开发

也可以把整个项目放在：

```text
你的仓库/.obsidian/plugins/knowgrove/
```

执行 `npm install` 和 `npm run dev` 后，在 Obsidian 中重新加载插件即可。

## 交互与主题

- 使用 Obsidian 原生 CSS 变量，不写死背景色、字体和主题色。
- 支持浅色、深色及修改了基础变量的第三方主题。
- 所有关键操作都有键盘焦点、ARIA 标签、空状态和错误提示。
- 浮层遵循减少动态效果的系统设置。

## 当前边界

- 一次选区应属于同一个 Markdown 语义块。对于跨多个段落的选区，插件会在选区末尾创建块 ID；Obsidian 最终嵌入范围仍以其块解析规则为准。
- 原文内容由原生块嵌入实时展示；评论文字由插件数据同步，不是多端协同编辑协议。只要插件数据和笔记一同正常同步，引用关系即可保持。
- 如果原文、块 ID 和选区前后文被同时彻底删除或改写，插件无法可靠判断新位置，会在手动检查中列为“需手动处理”。
- 删除原文时插件会保留引用记录，方便识别断链；删除目标笔记时会把该引用降级为“仅原文评论”。
- 属性审计来自当前 Vault 已存在的属性、覆盖率和值域；领域树建议则由用户选定的模型基于标题和现有分类汇总生成。低置信度结果不会绕过既有类型与枚举约束。
- 扫描发现的高覆盖属性默认只是可选建议，不会因为覆盖率较高就自动升级为全库必填规范。
- 属性规则支持“全局必填”和“按文档类型条件必填”；系统内置的 `创建时间` 只对 `输入资料` 必填，不会要求知识、项目、行动或输出笔记补写该字段。
- Base 的“已符合规范 / 待规范”清单来自插件最近一次完整审计，因此会与左侧两个指标保持一致；点击工作面或手动检查会刷新这份审计快照。
- 1.0.0 的工作空间 AI 只在当前 Vault 内发现和组织资料，不会自行联网调研或下载网页；外部研究、下载确认和来源入库将作为后续独立能力接入，避免在没有用户确认时写入外部内容。
